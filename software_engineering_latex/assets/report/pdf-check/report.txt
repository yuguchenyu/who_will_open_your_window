                      1   问题定义

1.1     项目背景与意义

      “谁能打开你的窗”是一个以低压力开场、渐进交流和表达自主权为主题的
课程软件项目。项目关注的不是通过算法替用户决定关系，而是让用户在自愿展
示资料的前提下发现交流对象，通过短纸条开启联系，再由本人决定是否回应、
继续交流以及使用 AI 表达建议。其核心问题可以概括为：如何在有限的课程开
发条件下，将人物发现、首次接触、持续对话和个人感受记录组织成一个规则清
晰、可恢复且不混淆真人与 AI 的交互闭环。
      陌生人交流可能面临开场困难、表达犹豫、回应含义不明确以及互动节奏不
一致等问题。本项目把这些情况作为设计假设，而非已经通过用户调研证明的普
遍结论。现有仓库未提供问卷、访谈原始记录、用户规模或长期使用统计，因此
报告不据此推断市场需求、满意度提升或关系成功率。后续若开展用户研究，应
补充样本来源、研究过程和可复核结果。

1.1.1    基于 NABCD 的问题分析

               。目标使用场景是愿意尝试文字交流、但希望保留开场和回应
        需求（Need）
选择权的用户体验课程原型。用户需要了解对象身份类型，能够简短介绍自己、
决定是否接收陌生人纸条，并在交流过程中自行编辑和发送内容。项目不提供真
实身份认证，注册账号不能等同于已验证的现实身份。
        方法（Approach）。系统采用浏览器与 Node.js 服务端协同的结构，使用
SQLite 按账号保存资料及互动数据。两段介绍经用户同意后由文本模型提取固
定词表标签，服务端据此计算双向参考契合度，筛选并加权抽取候选对象。用户
选择“喜欢”后加入收藏，再通过纸条和回信建立对话。真人消息由参与者本人
发送，虚拟人物回复由服务端调用模型生成，两条流程在界面和业务状态中明确
区分。
        收益（Benefit）。短纸条、接收偏好、收藏资格与每日额度使首次接触有明
确边界；可编辑的建议降低组织语言的操作负担，但不自动代替用户发言。聊
天、场景、头像及立绘构成统一体验，心笺与回望则让用户记录自己的感受。上
述收益属于功能设计意图，不能写成已量化验证的心理改善或社交效果。

1.1.2    问题边界与伦理约束

      系统中的真人账号与 AI 虚拟人物并非同一类对象。真人纸条和消息属于账
号之间的实际通信；虚拟人物来信注入、模拟日期推进、对方意愿设置及周期揭
晓属于 Demo 状态操作。AI 不冒充真人收件人回信，演示面板也不代表真人后
台管理能力。
        匹配百分数仅表示固定标签条件的契合程度，不是恋爱成功概率。意图解
释、交流参考分和情绪预测只是依据有限文本生成的参考信息，不能确认对方真
实想法，模型自评置信度也不是经过校准的统计概率。涉及未成年虚拟角色的设
定应保持适龄的日常、学习、兴趣和友谊交流；现有人设提示不等同于完备的未
成年人保护机制。
        账号间访问校验与产品中的“私密”语义也需要区分。私人心笺不作为对方
可见的关系结论，不发送给文本模型，但记录仍存于未加密的服务端数据库。具
备数据库文件读取权限的人能够查看记录，不能承诺端到端加密、数据库管理员
不可见或绝对隐私。


1.2     项目基本目标

      本项目的基本目标是实现一个可在本地复现的完整交流原型，以当前源码
可确认的能力为范围，而不是直接建设可公网运营的交友平台。具体目标如下。

 1. 建立账号与数据基础：支持注册、登录、退出和单账号单有效会话，服务端
      按账号持久化资料、收藏与互动状态；换设备登录后能读取该账号数据，原
      会话在后续请求时失效。

 2. 实现人物发现与首次接触：支持介绍校验、AI 标签提取、双向评分、加权
      抽取和收藏管理；通过长度、接收偏好、待回应状态和每日额度限制纸条投
      递。

 3. 区分真人通信与虚拟互动：真人收件人本人回信后建立双方会话；虚拟人物
      通过明确标记的模型流程回应，不用模型伪造真人消息。

 4. 提供可控的表达辅助：生成三项可编辑回复建议，支持四种回复风格及自行
      输入；分析期间真人用户仍能手动发送，过期分析不覆盖新消息的结果。

3.3     关键数据结构定义

3.3.1   字段类型与约束记法

      以下数据字典逐字段对应实际 DDL。T、I、B 分别表示 TEXT、INTEGER、
BLOB；N 表示显式 NOT NULL，PK 表示主键，U 表示唯一，FK 表示声明外键，
D 表示默认值。所有声明 FK 都带 ON DELETE CASCADE，下表不重复写出。普
通 SQLite 表的 TEXT 主键仅声明 PK 不等于显式非空，因此字典单独标明未显
式 N；应用仍写入有效编号。时间通常为 Unix 毫秒，day 则为日期文本。立绘
updated_at 同时是单调版本，未必严格等于物理时间。JSON 为 TEXT，数据库未
声明 json_valid 检查，布尔整数也未统一声明 0/1 CHECK。

3.4.1   标签提取与双向匹配公式

较不是数据库版本式并发控制。

取在注册函数事务之后，不是全部注册和模型等待都处于一个事务。密码用独立
盐进行 scrypt 派生并恒定时间比较；账号不存在也进行虚拟摘要派生，减少耗时
探测差异。登录按真实 TCP 对端地址计失败窗口，15 分钟内 IP/账号 10 次或全
IP 30 次限流。成功时事务内将旧会话 active=0 并记录替换设备，清理旧会话后
插入新会话，部分唯一索引保证单活跃。只清 IP/账号失败键，不清全 IP 键，避
免用已知账号成功登录不断解除 IP 限制。浏览器持原令牌、数据库存 SHA-256
摘要，当前有效期 30 天。旧设备下一次请求收到 SESSION_REPLACED，不是
主动注销推送。

制；也需要重新评估模型外发授权与服务商政策。当前数据库文件可被具备文件
权限的人读取，不能以账号隔离声称绝对保密。

5.4.2   一致性与性能

      同步 SQLite 与密码派生可能阻塞高负载下的事件循环；历史性能仅覆盖本
地小规模、模拟模型条件。生成任务目前不是跨实例持久化队列，重启将运行中
任务标记失败而非自动续跑。参考分缓存、水位和异步隐私复核仍有改进空间；
部分布尔参数需严格类型校验，注册资料和迁移需要进一步统一原子性与备份
策略。这些是已知改进事项，不计入本报告的完成能力。

6.1.1   业务规则需要明确的状态边界

和测试中的非法动作前后状态比较说明：可靠交互不能只靠按钮置灰，还需要在
写入位置执行规则。

6.1.2   异步结果不等于当前有效结果

      模型生成与用户继续输入、切换风格或修改图片可能同时发生。消息编号、
当前风格、参考图摘要和目标图片版本提供了判断结果是否仍适用的条件。文本
分析可以丢弃过期响应；图片生成还必须经过私有预览和确认保存。两类处理共
同体现了一个原则：上游请求成功并不能跳过业务一致性检查。

6.1.3   降级和恢复应成为设计的一部分

      真人发言不依赖模型代回，普通动作与模型并发额度分离；虚拟回复失败保
留任务，重试不重复写消息；生成失败不覆盖已有图。这些实现将失败纳入正常
控制流，而非只提供一个通用报错。数据库事务和重启状态处理使恢复条件可解
释，但仍不能推导出已经具有生产级灾难恢复能力。

6.1.4   证据的适用范围需要随版本维护

      早期文档的“没有账号、没有真人通信”不能无日期地用于当前版本；历史
测试环境和性能也不能改标签后当作本次结果。源码行数可以说明项目规模，却
不能说明成员贡献。报告将当前源码、模拟测试、历史测量、截图和未取得的用
户反馈分开，有助于发现描述漂移，并避免把课程演示证据过度推广。

export function matchScore(a, b) {
    // 分别计算双方期望被满足的比例；任一方向没有交集时不予匹配。
    const towardB =
         a.desiredTags.filter((t) => b.selfTags.includes(t)).length /
         a.desiredTags.length;
    const towardA =
         b.desiredTags.filter((t) => a.selfTags.includes(t)).length /
         b.desiredTags.length;
    if (!towardA || !towardB) return 0;
    return Math.round((100 * (towardA + towardB)) / 2);
}
