                       任务书

一   总体要求

1. 综合运用软件工程的思想，协同完成一个软件项目的开发，掌握软件工程相
    关的技术和方法；

2. 组成小组进行选题，通过调研完成项目的需求分析，并详细说明小组成员的
    分工、项目的时间管理等方面。

3. 根据需求分析进行总体设计、详细设计、编码与测试等。


二   基本内容

    根据给出的题目任选一题，自行组队，设计与开发的软件过程必须包括：

1. 问题概述、需求分析：正确使用相关工具和方法说明所开发软件的问题定义
                                                     ；
    和需求分析，比如 NABCD 模型，Microsoft Visio，StarUML 等工具（20%）

2. 原型系统设计、概要设计、详细设计：主要说明所开发软件的架构、数据结
    构及主要算法设计，比如墨刀等工具（35%）；

3. 编码与测试：编码规范，运用码云等平台进行版本管理，设计测试计划和测
    试用例（30%）；

4. 功能创新：与众不同、特别吸引用户的创新（10%）；

5. 用户反馈：包括用户的使用记录，照片，视频等（5%）。

                3    概要设计和详细设计

3.1    项目概述与总体架构

      “谁能打开你的窗”是一款以低压力社交为目标的交流应用，将发现伙伴、
纸条联系和日常聊天串联起来。用户填写个人介绍和相遇偏好后，可以发现合适
的对象、加入收藏，再通过纸条开启交流。
      系统采用 B/S 架构，整体组成如图3-1所示。浏览器提供操作界面，Node.js
服务端处理业务，SQLite 保存应用数据，外部 AI 服务为表达辅助、虚拟回复和
立绘生成提供支持。

                          用户界面
               相 遇、 纸 条、 聊 天、 心 笺 回 望 与 形 象 设 置
                                用户请求

                           服务端接口
                    接 收 用 户 操 作， 返 回 业 务 结 果


                    核心业务
          账号与匹配、纸条与聊天、虚拟互动、AI 辅助与形象管理

            数据存储                               AI 服 务
          用 户 资 料、 互 动                  文 本 辅 助、 虚 拟
          记录与媒体资源                       回复与立绘生成

                       图 3-1   项目总体架构


      真人交流是系统中的核心场景：用户通过相遇功能发现合适的伙伴，将感兴
趣的对象加入收藏，并以纸条发起联系。对方接受纸条并回信后，双方即可进入
聊天，逐步从初次相识发展为持续交流。
      收藏与纸条分开发现和聊天，让双方了解来意后选择是否交流。未获接受时
仍可浏览其他对象，保留低压力的选择空间。
      虚拟互动提供内置人物交流、心笺与回望体验，作为日常表达与感受回顾的
补充。AI 提供表达建议，由用户选择采用并发送；耗时任务展示进度，失败时
提示重试。

3.1.2   HTTP 请求处理与接口契约

    接口把页面上的查看、选择和发送转为可检查的业务操作。服务端先接收请
求并识别所访问的内容，再按查询或提交进入相应流程，如图3-3所示。需要身
份的操作先确认登录状态，涉及他人或会话的内容再检查访问权限。

                接 收 请 求： 识 别 访 问 内 容 与 操 作 类 型




         查询：页面、资源与记录                 提交：选择、文本与素材
         确认身份及可访问范围                  检查来源及输入是否合适




           处理业务：核对用户、资源与当前条件，查阅或保存结果



              返 回 结 果： 展 示 内 容、 处 理 状 态 或 失 败 原 因


             图 3-3   请求接收、业务检查与结果返回流程


     查询取得当前记录，提交表达一次明确选择。提交先检查来源与输入，再判
断业务条件。例如，服务端按会话编号定位交流，确认用户的参与者身份后读取
或发送消息。
     分层检查使不同问题有明确处理：未登录时引导登录，输入不合适时提示修
改，业务条件变化时返回当前结果，帮助用户决定下一步。

结果、会话和开场消息整体保存，让进入聊天时能够接续完整的来意与回应。
     会话关联双方，消息另关联发送者，业务据此检查读写资格。甲发送的消息
保留在甲乙的会话中，乙再次进入可接着阅读，双方按参与者身份访问交流记
录。
     交流参考按方向记录，分别呈现甲看乙与乙看甲的交流情况。已有结果按消
息进度复用，新消息到来后按需更新对应方向的分析。会话与参考通过外键形成
一对多关系，分析目标取自双方参与者，消息进度通过图中虚线所示的逻辑关系
驱动更新。
